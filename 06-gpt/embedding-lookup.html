Two tables, two questions

Independent lookups, until you combine them

token_embedding_table — indexed by which character (id 0–64). Answers "what is this?"
position_embedding_table — indexed by which slot (0–7). Answers "where is this?"

Nothing links these two tables together. They're queried separately, and stay separate, until forward() explicitly adds their outputs — a line your current code hasn't written yet.

65 rows × 32 columns

token_embedding_table

One row per character in the vocabulary, sorted low → high id. The outlined rows are the ones "First Ci" actually touches — everything else exists but sits unused this block.

'i' appears twice in this block — position 1 and position 7 — and both reads pull the exact same row, id 47. Same character, same vector, no matter where it sits.

8 rows × 32 columns

position_embedding_table

Small enough to show in full — every row this table will ever have for this model.

Row 2 means "I'm the 3rd token in the block," full stop — whether that slot holds an 'r', a '!', or a newline.

The merge — one slot at a time

For every slot in "First Ci": one row pulled by character id, one row pulled by position, added elementwise into a single fused vector.

Right now forward() only computes the first column above (tok_emb) and feeds it straight to lm_head — the position row and the + aren't wired in yet.

32 → 65

lm_head

One shared Linear(32, 65), applied identically at every slot. Here it's run on slot 0's combined vector — "F" at position 0.

— lm_head → 65 logits

One raw score per character in the vocabulary — higher means "more likely to come next." On an untrained model these are close to noise, which is exactly why the loss starts high and training exists at all.

table lookup → table lookup → + → lm_head. That's the whole path from a character on disk to a next-character guess — and the line you're about to add to forward().
