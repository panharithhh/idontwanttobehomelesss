Bigram to GPT, Stage by Stage

Every step of Karpathy's "Let's build GPT", from a single embedding table to a full transformer — grounded in the actual reference code from his ng-video-lecture repo, walked through with your model's real vocabulary.

Stage 1 · before any model exists

Text → integers

Everything starts by treating the training text as a flat stream of characters, not words. chars = sorted(set(text)) finds every unique character that appears anywhere in input.txt — 65 of them, for tinyshakespeare — and assigns each one an integer id (stoi) and the reverse mapping back (itos). get_batch() then slices out batch_size random windows of length block_size, where y is just x shifted one character to the right — the target at every position is simply "the next character."

chars = sorted(list(set(text))) stoi = { ch:i for i,ch in enumerate(chars) } itos = { i:ch for i,ch in enumerate(chars) } # x: (B, T) block of characters, y: x shifted one to the right ix = torch.randint(len(data) - block_size, (batch_size,)) x = torch.stack([data[i:i+block_size] for i in ix]) y = torch.stack([data[i+1:i+block_size+1] for i in ix])

Nothing here is learned — it's bookkeeping. Every model below receives (x, y) pairs shaped exactly like this.

Stage 2 · the absolute starting point

Pure bigram: one embedding table, nothing else

Karpathy's very first working model skips n_embd and lm_head entirely: nn.Embedding(vocab_size, vocab_size). Look an id up, and the row you get back is the logits — 65 numbers straight out of the table, no projection step at all.

self.token_embedding_table = nn.Embedding(vocab_size, vocab_size) def forward(self, idx, targets=None): logits = self.token_embedding_table(idx) # (B,T,C) — already the logits

This is the whole model. Its ceiling is exactly what "bigram" implies: predicting character N+1 from character N alone, nothing earlier.

Stage 3 · your current idk.py

Decoupling width: n_embd + lm_head

The next move doesn't change what the model can see — still just the current character — it changes how much room the model has to represent it. Instead of jumping straight from character id to 65 logits, insert a hidden width, n_embd, in between. token_embedding_table now outputs a 32-number vector; lm_head, a separate Linear(32, 65), does the projection to logits.

This refactor is exactly where your own forward() sits right now, and it's what unlocks everything that follows — a hidden vector is something you can add other information into before projecting to logits. That's the seam position embeddings slot into next.

Stage 4 · covered in depth in the companion piece

Position embeddings: adding "where" to "what"

position_embedding_table = nn.Embedding(block_size, n_embd) — one row per slot (8 of them), independent of which character occupies that slot. x = tok_emb + pos_emb fuses "what character" with "where in the block" into a single vector before lm_head ever sees it.

Full breakdown — the 65-row table, the reused rows, the elementwise add worked out slot by slot — lives in Embedding Lookup, Block by Block.

Stage 5 · the motivating problem

The ceiling: tokens still can't talk to each other

Here's the trap: even with position embeddings wired in, lm_head is applied to each slot's vector independently. The vector at slot 4 knows "I am 't', and I am the 5th slot" — but nothing about what sat at slots 0 through 3. Stack a hundred more linear layers on top and that stays true: no layer built purely from per-token math ever lets one token look at another.

To predict well, the model needs slot 4 to be able to pull information from slots 0–3 — selectively, based on what's actually relevant, not just "average everything blindly." That selective pulling is what attention is.

Stage 6 · the bridge to attention

The mathematical trick: averaging the past

Before real attention, Karpathy builds the simplest possible version of "gather information from earlier slots": a running average. Slot i's new vector becomes the mean of slots 0..i — cheap, and, crucially, it only looks backward (slot 4 never sees slot 5, since slot 5 doesn't exist yet when slot 4 is being predicted from).

The naive way is a double for-loop. The fast way is one matrix multiply: build a lower-triangular matrix of ones, normalize each row to sum to 1, and multiply it against x.

wei = torch.tril(torch.ones(T, T)) wei = wei / wei.sum(1, keepdim=True) xbow = wei @ x # (T,T) @ (B,T,C) -> (B,T,C), each row now a running mean

This grid is exact — no learned parameters, just arithmetic. For 5 tokens, row i is 1/(i+1) across columns 0..i, zero after:

Every token gets equal weight — token 0 matters to slot 4's average exactly as much as token 3 does. That's the limitation real attention fixes: which past tokens matter shouldn't be fixed, it should depend on content.

Stage 7 · the core idea of the whole architecture

Self-attention: replacing "equal weight" with "earned weight"

Same shape of computation — a row of weights per slot, multiplied against something, summed — but now the weights are computed from the data itself instead of fixed at 1/(i+1). Every token produces three projections of its own embedding:

query — "what am I looking for?"  ·  key — "what do I contain?"  ·  value — "what do I actually pass along?"
self.key = nn.Linear(n_embd, head_size, bias=False) self.query = nn.Linear(n_embd, head_size, bias=False) self.value = nn.Linear(n_embd, head_size, bias=False) k = self.key(x); q = self.query(x); v = self.value(x) # each (B,T,head_size) wei = q @ k.transpose(-2,-1) * head_size**-0.5 # (B,T,T) — the affinities wei = wei.masked_fill(self.tril[:T,:T] == 0, float('-inf')) wei = F.softmax(wei, dim=-1) # rows now sum to 1 out = wei @ v # (B,T,head_size)

Worked through your own block — "First", 5 slots, focusing on slot 4 ('t'), since that's whose output predicts the 6th character:

These are key and value for all 5 positions, and query for position 4 only — position 4's query is the one whose prediction we're tracing.

Raw affinities — query[4] · key[j], scaled — then masked (positions after 4 don't exist yet, shown blank):

After softmax — a real probability distribution over the 5 positions, summing to 1:

The scale factor * head_size**-0.5 matters more than it looks: without it, as head_size grows, dot products grow with it, softmax saturates toward a one-hot spike, and gradients through it vanish. Dividing by √head_size keeps the pre-softmax variance near 1, so the distribution starts out genuinely soft.

Stage 8 · running several of these in parallel

Multi-head attention

One head asks one kind of question. Real transformers run several heads side by side — each with its own independent key/query/value weights, each free to specialize in a different kind of relationship — then glue the results back together with a concatenation and a final linear projection back to n_embd width.

self.heads = nn.ModuleList([Head(head_size) for _ in range(num_heads)]) self.proj = nn.Linear(head_size * num_heads, n_embd) out = torch.cat([h(x) for h in self.heads], dim=-1) # (B,T, num_heads*head_size) out = self.proj(out) # back to (B,T,n_embd)

If n_embd = 32 and you pick n_head = 4, each head gets head_size = 8 — four 8-wide "opinions" concatenated back into one 32-wide vector.

Stage 9 · communication vs. computation

Feedforward: thinking alone about what was gathered

Attention is the only place tokens exchange information with each other — Karpathy calls it "communication." Feedforward is the opposite: a plain per-token MLP, applied identically and independently to every slot, with no cross-token mixing at all — "computation." It gives each token a chance to process what attention just handed it.

nn.Sequential( nn.Linear(n_embd, 4 * n_embd), nn.ReLU(), nn.Linear(4 * n_embd, n_embd), )

The 4× expansion in the middle is a convention carried over from the original Transformer paper — more room to compute in, then compressed back to n_embd before leaving.

Stage 10 · assembling communication + computation

Residual connections, LayerNorm, and the Block

Two more ingredients before attention and feedforward can be safely stacked many times deep:

Residual (skip) connections — instead of x = sublayer(x), write x = x + sublayer(x). The unmodified x always has a direct path through, so gradients have a highway back to early layers even when a deep stack would otherwise struggle to train at all.

LayerNorm — rescales each token's own vector to stable mean/variance before it enters a sublayer. Modern practice (what this repo uses) applies it before attention and feedforward, not after — "pre-norm" — which trains more reliably than the original paper's "post-norm" layout.

def forward(self, x): x = x + self.sa(self.ln1(x)) # attention, with a skip connection x = x + self.ffwd(self.ln2(x)) # feedforward, with a skip connection return x

Stage 11 · GPTLanguageModel

Stack N blocks, and that's a GPT

The full model is almost entirely the pieces already built, repeated: token + position embeddings go in, n_layer copies of Block run in sequence, one final LayerNorm cleans things up, and lm_head projects to logits — exactly as it always has, just now reading a vector shaped by every earlier token instead of only its own identity and position.

self.token_embedding_table = nn.Embedding(vocab_size, n_embd) self.position_embedding_table = nn.Embedding(block_size, n_embd) self.blocks = nn.Sequential(*[Block(n_embd, n_head) for _ in range(n_layer)]) self.ln_f = nn.LayerNorm(n_embd) self.lm_head = nn.Linear(n_embd, vocab_size) def forward(self, idx, targets=None): tok_emb = self.token_embedding_table(idx) pos_emb = self.position_embedding_table(torch.arange(T)) x = tok_emb + pos_emb x = self.blocks(x) x = self.ln_f(x) logits = self.lm_head(x)

Stage 12 · sampling text out

generate(): why context gets cropped

Same loop as your bigram model's generate() — predict, sample, append, repeat — with one addition that becomes necessary the moment position_embedding_table enters the picture: that table only has block_size rows. Feed it a sequence longer than block_size and torch.arange(T) asks for a position row that doesn't exist. So every step, the context gets cropped to the last block_size characters before the forward pass runs.

idx_cond = idx[:, -block_size:] # keep only what position_embedding_table can index logits, loss = self(idx_cond) logits = logits[:, -1, :] # only the last position's prediction matters probs = F.softmax(logits, dim=-1) idx_next = torch.multinomial(probs, num_samples=1) idx = torch.cat((idx, idx_next), dim=1)

Stage 13 · what changes at real scale

From this toy GPT to ChatGPT

Structurally, this is a GPT — the same embeddings, attention, feedforward, residuals, and LayerNorm scale up essentially unchanged. What's different at real scale:

tokenizerCharacter-level here; real GPTs use byte-pair encoding (BPE) — subword chunks, so vocab_size is tens of thousands, not 65, and one "token" is often several characters.
scalen_embd, n_head, n_layer, and block_size all grow by orders of magnitude — GPT-3 uses 96 layers, 12288-wide embeddings, 2048-token context.
dataNot one Shakespeare file — hundreds of billions of tokens scraped from the web, books, and code.
after pretrainingWhat you've built here is pretraining — next-character prediction over raw text. ChatGPT adds instruction-tuning and RLHF on top: further training specifically to follow instructions and prefer helpful responses, using human feedback rather than just "predict the next token."

Everything upstream of that last row — every mechanism on this page — is the actual foundation every one of those larger models is built from.

idx → embed → attend → compute → project. Six stages, one repeated Block, and a crop in generate() — that's the entire architecture, at any scale.
